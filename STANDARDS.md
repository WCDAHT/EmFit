# Brunch Standards

Four projects taught us these rules the hard way. COMRADE, FENDER, Hashbrown, and Message-Maestro each repeated the same mistakes: scattered color literals, monolithic files, print-debugging, README drift. This document is the residue. What worked, what didn't, codified before we forget.

A living guide. When you deviate, leave a comment. When the deviation repeats, update this doc.

**Stack:** Rust + Tauri 2 + Svelte 5 (TypeScript), built with Vite. The Rust side is a two-crate workspace (`*-core` for logic, `src-tauri` for the Tauri shell); the frontend is a Svelte app in `frontend/`. We migrated off Rust/Slint after the first round of apps: the dynamic, canvas-heavy UIs we kept needing (investigator boards, draggable cards, edges between nodes) fought the retained-mode toolkit, the hand-roll budget grew without bound, and Slint's Royalty-Free attribution obligation rode on every binary. A webview frontend gets us a mature component ecosystem (Svelte Flow for node/edge boards, native form controls, accessibility for free), small compiled bundles, and a permissive license. The Brunch repo is the template; scaffold new apps from it.

**Reference projects, one line each:**
- **COMRADE** (Python/tkinter): graph viewer for people, notes, and relationships. Card-and-canvas UI, ZIP+CSV persistence. The archetypal "investigator board" - the use-case that drove the Svelte Flow choice.
- **FENDER** (Python/tkinter): forensic GPS extractor for vehicle telematics. Plugin-style decoders, dual GUI/CLI.
- **Hashbrown** (Python/tkinter): three-tool video utility (redact audio, amplify, trim). FFmpeg wrapper with a shared launcher.
- **Message-Maestro** (PyQt6 at commit `6640d75`, the last working version): conversation viewer/tagger for chat exports. Pluggable parsers, sidecar JSON tags, PDF export.

## 1. Repo Layout

Every app is one Cargo workspace (two Rust crates) plus a Svelte frontend. The `*-core` / `src-tauri` split is the single most useful boundary in the stack: it forces clean APIs, keeps the logic testable headless, and leaves room for a CLI or future port without rewriting. The webview frontend is the third leg; it talks to the shell only through typed IPC commands.

The three code peers (`<app-name>-core/`, `src-tauri/`, `frontend/`) sit beside the two project manifests. `Cargo.toml` and `package.json` stay at the root because the CLIs resolve their code from there: `cargo`/`tauri` find `src-tauri/` relative to the root, and the npm scripts `cd frontend` before running Vite/svelte-check (so the Vite root is `frontend/`). Everything else web - `index.html`, the Vite/Svelte/TS configs, and `src/` - lives under `frontend/`.

**Target structure:**

```
<app-name>/
+-- Cargo.toml              # workspace root; shared Rust dep versions
+-- package.json            # frontend deps + scripts (dev -> vite frontend, tauri)
+-- <app-name>-core/        # all logic; no UI/Tauri deps; testable headless
|   +-- Cargo.toml
|   +-- src/
|   |   +-- lib.rs          # public API for the shell crate
|   |   +-- model/          # data types (serde-derived structs)
|   |   +-- parser/         # input format handling (one file per format)
|   |   +-- service/        # operations: task, case, export, persistence
|   |   |   +-- task.rs     # Progress enum + CancellationToken (sec 3.5)
|   |   |   +-- case.rs     # Sidecar JSON persistence with atomic writes (sec 4.5)
|   |   |   +-- export.rs   # Exporter trait for PDF/KML/Excel/PNG (sec 4.6)
|   |   +-- error.rs        # crate-level Error enum (thiserror)
|   +-- tests/              # integration tests against the public API
+-- src-tauri/              # Tauri shell (thin Rust); the only crate that links Tauri
|   +-- Cargo.toml          # depends on -core; lib + bin targets
|   +-- build.rs            # tauri-build
|   +-- tauri.conf.json     # window, bundle, CSP, identifier, frontendDist -> ../frontend/dist
|   +-- capabilities/       # per-window permission grants (least privilege)
|   |   +-- default.json
|   +-- icons/              # generated by `tauri icon` (committed)
|   +-- src/
|       +-- main.rs         # binary entry; suppresses console; calls lib::run
|       +-- lib.rs          # run(): builder, plugins, invoke_handler
|       +-- commands.rs     # #[tauri::command] glue -> core (sec 3.4)
|       +-- error.rs        # Serialize-able command error wrapping core::Error
+-- frontend/               # Svelte frontend (Vite root)
|   +-- index.html          # Vite entry; mounts #app, sets initial data-theme
|   +-- vite.config.ts      # tuned for Tauri (port 1420, strictPort, fs.allow ..)
|   +-- svelte.config.js
|   +-- tsconfig.json
|   +-- src/
|       +-- main.ts         # mounts App, applies theme before first paint
|       +-- App.svelte      # root view
|       +-- styles/
|       |   +-- theme.css   # design tokens as CSS custom properties (sec 2)
|       |   +-- global.css  # @font-face, base reset, icon webfont
|       +-- lib/
|       |   +-- ipc.ts      # typed wrappers around invoke() (sec 3.4)
|       |   +-- log.ts      # console -> Rust log-file bridge (sec 4.2)
|       |   +-- theme.ts    # data-theme toggle + persistence (sec 2.2)
|       |   +-- components/ # reusable: Button.svelte, Icon.svelte, dialogs
|       |   +-- views/      # screen-level: Sidebar.svelte, DetailPane.svelte
|       +-- assets/         # fonts, license texts bundled by Vite
+-- docs/                   # user-facing docs (usage, tutorials)
+-- analysis_todo.md        # in-repo backlog (see sec 5.4)
+-- README.md
```

There's one `STANDARDS.md` per workspace, here at the Brunch repo root. Apps reference it by relative path or link from their READMEs. Don't try to symlink. Windows treats that as an admin operation outside developer mode.

**Guidelines:**
- **Core never imports Tauri or any UI.** `cargo check -p <app>-core` must succeed with `src-tauri/` deleted. The core crate has no `tauri`, no `serde`-for-IPC-only types, no knowledge that a webview exists.
- **The shell is thin.** `src-tauri` owns window setup, plugin registration, and `#[tauri::command]` glue. Business logic that creeps into a command belongs in a core `service` (sec 3.4). If `commands.rs` grows past glue, that's the smell.
- **One concept per file in `core/`.** `model/conversation.rs`, `parser/discord.rs`, `service/pdf_export.rs`. Don't accumulate `utils.rs`. That's where files go to become 1000 lines and never get refactored.
- **`lib/components/` vs `lib/views/`:** A *component* is reusable across views (`MessageBubble`, `IconButton`, `TimeField`). A *view* is screen-level and app-specific (`ConversationListView`, `SettingsDialog`). Promote on the second actual use, not on speculation.
- **Workspace dependencies (Rust):** declare versions once in the root `Cargo.toml` under `[workspace.dependencies]`, reference them from member crates with `tauri = { workspace = true }`. **Frontend dependencies** are pinned by caret range in `package.json`; the committed `package-lock.json` is the lockstep guarantee.

## 2. Visual Design Language

### 2.1 Theme tokens

**Every color, font size, spacing value, and corner radius lives in `frontend/src/styles/theme.css` as a CSS custom property, and is referenced semantically. Never inlined.**

This is the single biggest lesson from the reference projects. Message-Maestro had a centralized `theme.py` *and* hardcoded `#1d9bf0` strings sprinkled through `message_bubble.py` and `conversation_item.py`. Changing the accent color required grep-and-pray.

Defaults:
- No color literal (`#ff8c42`, `red`) outside `theme.css`. Every other file references tokens (`var(--accent)`, `var(--surface-raised)`).
- No font-size literal outside `theme.css`. Use `var(--font-size-body)`, not `13px`.
- No magic spacing. Use `var(--space-2)`, `var(--space-3)`, etc.
- Exceptions: structural `0` and `1px` (e.g. a 1px divider). Anything `2px` and up goes through a token.
- For widths and heights, prefer content-driven sizing (flexbox, `min-content`, `auto`). When you do need a fixed size, define a token rather than hardcoding in the component's `<style>`.

CSS custom properties make this enforceable: tokens cascade, so a component's scoped `<style>` block reads `var(--accent)` and the value resolves from `:root`. A stray hex literal stands out in review.

### 2.2 The Brunch theme (default)

The token *names* and their semantic roles are the contract. Apps may retune values; they should not redefine the semantic names.

Brand: **Brunch orange `#ff8c42`** is the canonical accent across every app spawned from this template. Status colors are the GitHub Primer palette (positive `#3fb950`, warning `#d29922`, danger `#f85149`). Selection is Windows 11 SystemAccentColor `#0078d4`, kept distinct from accent so "the user chose this" reads differently from "this is branded."

Two palettes ship in one `theme.css`, switched by the `data-theme` attribute on `<html>`. **Dark is the default**, with warm grey-green surfaces (`#1b1f23` base, GitHub-dimmed lineage) to avoid halation during long analysis sessions. **Light is crisp paper-white** with deliberately stronger borders, tuned so panel structure remains visible when projected in a courtroom or lab under ambient light. Accent, selection, status, and the category palette stay constant across modes (they live only in `:root`; the `[data-theme="light"]` block overrides only what changes).

`frontend/src/styles/theme.css` is the canonical token list. `frontend/src/lib/theme.ts` owns the switch: it reads a persisted choice (falling back to the OS `prefers-color-scheme`, then dark), sets `data-theme` before first paint via `main.ts`, and exposes `toggleThemeMode()` for a settings toggle. Don't set `data-theme` by hand at call sites.

Groupings in `theme.css`:
- **Surfaces, borders, text** (swap on mode)
- **Accent** (Brunch orange, brand) and **selection** (Windows blue, "user picked this"); kept distinct, both constant across modes
- **Status** (positive / warning / danger / info, GitHub Primer)
- **Chat bubbles, highlights**
- **Typography, spacing (4pt scale), radii, component sizing**
- **Category palette** (eight named tokens; ordered so adjacent categories are maximally distinguishable, brand orange at slot 8 so it doesn't appear in small charts)

**Selection vs accent usage rule.** `--accent` is for primary actions and brand affordances (the app's main CTA button, the current-case chip in the title bar, brand callouts). `--selection` is for "the user picked this thing" state (selected sidebar row, focused message outline, keyboard focus ring, multi-select highlight). Don't unify them; the distinction is what keeps the brand surface readable when half the UI is selected.

### 2.3 Category palettes (data colors)

For tags, card colors, chart series. Anything where a *set* of distinguishable colors is needed. The template exposes `--category-1` through `--category-8`. Use them in order; don't pick arbitrary new colors for new categories. Distilled from COMRADE's `CARD_COLORS` and Message-Maestro's tag palette. To iterate them in TypeScript, read the computed values or keep a parallel array of the variable names - don't fork the hex values into JS.

When you need more than 8 categories, first ask whether categorization is the right UI.

### 2.4 Typography

- **Bundle one font, self-hosted.** Inter (regular + semibold) is a fine default and what the template ships. Tabler, IBM Plex, and Source Sans are equally fine. Pick one per app, drop the `.otf`/`.ttf` in `frontend/src/assets/fonts/`, and declare it with `@font-face` in `global.css` (`src: url("../assets/fonts/Inter-Regular.otf")`). Vite emits the bytes into `dist/` and the app ships them - no system font dependency, no CDN/runtime fetch. Use `font-display: block` to avoid a fallback-font flash on the first frame.
- **Weight:** Regular (400) for body, SemiBold (600) for headers and emphasis. Tokens: `--font-weight-regular`, `--font-weight-semibold`.
- **Line height:** browser default. Override only with a comment explaining why.

### 2.5 Icons

- **App icon: one bespoke SVG per app.** COMRADE's `group.svg` and FENDER's `car.svg` are the model. Drop a square source SVG at the repo root and run `npx tauri icon ./app-icon.svg` - it generates the full platform icon set (`.ico`, `.icns`, PNGs) into `src-tauri/icons/`, which `bundle.icon` in `tauri.conf.json` references. Commit the generated icons.
- **UI icons: Bootstrap Icons via the `bootstrap-icons` npm package.** It ships both a webfont (used through `Icon.svelte`: `<Icon name="folder2-open" />`, ~2,000 MIT-licensed glyphs) and the raw SVGs. Use the webfont for ordinary inline icons; import a raw SVG (`import x from "bootstrap-icons/icons/foo.svg?raw"`) when you need to recolor individual paths or animate a glyph - e.g. Svelte Flow node markers. Only the one webfont file is bundled; SVG imports are tree-shaken. If Bootstrap Icons' vocabulary doesn't fit, Tabler/Phosphor/Lucide have npm packages too; pick one per app.
- **We no longer vendor the SVG tree.** The old Slint template committed ~2,000 SVGs into `assets/`; the npm package supplies identical files, so vendoring them is dead weight. The package's `LICENSE` is mirrored to `frontend/src/assets/licenses/bootstrap-icons-LICENSE.txt` for the About panel (sec 5.6).
- **Icons over symbols/emoji.** COMRADE and Hashbrown leaned on raw emoji (a person glyph, a floppy disk). Real icons render consistently across platforms and DPI; emoji do not.
- **Size icons by context.** Glyphs are vector, so any size renders crisp; `Icon.svelte` defaults to `1em` so icons track surrounding text. Pass a px size only when chrome demands a fixed dimension.

### 2.6 Spacing & layout

- **4px base unit.** Multiples of 4 by default (`--space-1` = 4px ... `--space-7` = 48px). Reach for 6 or 10, ask whether 8 or 12 works first.
- **Dialog padding:** `--space-5` (24px) all around.
- **Form fields:** `--space-2` between label and input, `--space-3` between fields.
- **Prefer flexbox/grid for structure.** Let content drive size; reserve fixed dimensions for genuinely fixed chrome (title bar height, sidebar width) and token them.

## 3. Frontend (Tauri + Svelte)

### 3.1 Component conventions

- **One component per `.svelte` file** in `lib/components/` and `lib/views/`. File name matches the component in PascalCase: `MessageBubble.svelte`, `ConversationListView.svelte`.
- **`<script lang="ts">` always.** Declare a `Props` interface and destructure with `$props()`. Public props first, then local state (`$state`/`$derived`), then functions, then markup, then a scoped `<style>` block. Svelte scopes `<style>` to the component automatically - no class-collision discipline needed.
- **Events are callback props, not dispatchers.** Svelte 5 dropped `createEventDispatcher`; pass callbacks as props. **Past tense for events** (`onClick`, `onSelect`, `onValueChange`), **request-style for actions** the parent must approve (`onDeleteRequested`, `onSaveRequested`). The view emits requests; the controller decides whether to honor them. This is a Brunch convention carried over from the Slint template.

```svelte
<!-- lib/components/MessageBubble.svelte -->
<script lang="ts">
  interface Props {
    text: string;
    isSent: boolean;
    isHighlighted?: boolean;
    onTagRequested?: (tagId: number) => void;  // request: parent decides
  }
  let { text, isSent, isHighlighted = false, onTagRequested }: Props = $props();

  // Local derived state stays private to the component.
  const bubbleColor = $derived(
    isSent ? "var(--bubble-sent)" : "var(--bubble-received)"
  );
</script>

<div class="bubble" style:background={bubbleColor} class:highlighted={isHighlighted}>
  {text}
</div>

<style>
  .bubble { /* tokens only - no literals */ }
  .highlighted { outline: 2px solid var(--search-highlight); }
</style>
```

### 3.2 Native controls vs libraries

**Default to native HTML controls for behavioral widgets. Style purely visual containers yourself; reach for a library for genuinely complex behavior.**

- **Use native elements** for: `<button>`, `<input>`, `<select>`, `<textarea>`, checkboxes, sliders (`<input type="range">`). The browser gives you keyboard focus, accessibility, IME, and state machines for free. Re-style them with tokens; don't reimplement them. (This is the same lesson as the Slint template's "use std-widgets" rule - the platform's controls beat hand-rolled ones.)
- **Style your own** `<div>`/`<span>` for: cards, panels, dividers, headers, labels, decorative chrome - anything that's "just a styled box."
- **Reach for a library** when the behavior is a known hard problem: the **investigator board (cards + edges + pan/zoom + drag) uses [Svelte Flow](https://svelteflow.dev)** - do not hand-roll node dragging, edge routing, or hit-testing. Virtualized long lists, rich-text editing, and date pickers are the same kind of call: pull a maintained library rather than grow the hand-roll budget.

The earliest Slint template hand-rolled buttons. It was wrong - within a week we needed a scrollbar, then a focusable text input. The hand-roll budget grows without bound. The web platform already solved most of this; use it, and use libraries for the parts it didn't.

### 3.3 State management

- **The Rust side owns truth.** Frontend state is a *projection* of what the core knows. Don't keep a second source of truth in the webview that can drift from disk.
- **Component-local state with runes.** `$state` for mutable local data, `$derived` for computed values, `$effect` sparingly (and never to sync state you could derive).
- **Cross-view shared state in a `.svelte.ts` module.** When two views need the same state, put it in a small module that exports runed state (e.g. `export const session = $state({...})`), not a tangle of props threaded through five layers. Reach for this on the second sharer, not the first.
- **Fetch from the core, don't mirror it.** Load data through `ipc.ts`, render it, and write changes back through commands. The webview is a cache of core state, explicitly refreshed - not the owner.

### 3.4 The shell<->core boundary (commands)

The webview's only way into Rust is a `#[tauri::command]`. This is the Tauri analogue of the old Slint callback wiring, and the same discipline applies.

- **Commands are thin glue.** Parse/validate args, call a core `service`, map the result to a `Serialize` type or a `CommandError`. No business logic. If a command is more than a few lines, the logic belongs in `*-core`.
- **Errors that cross IPC must be `Serialize`.** Keep a shell-level `CommandError` (in `src-tauri/src/error.rs`) that wraps `core::Error` via `#[from]` and serializes to its display string. Don't make core errors `Serialize` to satisfy the boundary; that's the shell's job.
- **App commands are registered once;** list them in `tauri::generate_handler![...]` in `lib.rs` and they're invokable from the webview. Your own `#[tauri::command]`s do *not* need a capability entry - the capability/permission system (sec 3.6) gates only **plugin** commands (`dialog:`, `opener:`) and **core** APIs. Don't confuse the two: adding a permission for your own command is a no-op, and forgetting to register it in the handler is what makes it unreachable.
- **One typed wrapper per command in `frontend/src/lib/ipc.ts`.** The rest of the Svelte code calls `greet(name)`, never `invoke("greet", { name })`. This keeps command names in one place, type-checks every call, and makes the frontend's dependency surface greppable.

### 3.5 Async work, progress, and cancellation

Long work runs on the Rust side, off the webview's single thread; updates stream back over IPC.

- **Never block.** A command that touches disk, network, or takes >16ms should be `async fn` (Tauri runs it on its async runtime) or offloaded with `tauri::async_runtime::spawn`. Blocking the command handler freezes the IPC bridge.
- **Progress streams over a `Channel`, not polling.** Use `tauri::ipc::Channel<Progress>`: the frontend passes a channel into the command, the Rust side sends typed `Progress` events, the frontend's `onmessage` updates state. Use the `Progress` enum from `<app>-core::service::task` (`Started`, `Tick`, `Finished`, `Failed`) - don't reinvent it per app, don't use stringly-typed status. Each `Started` opens a *phase* and carries a human-readable `message` (set once per phase, not per `Tick`) plus an optional `total`; a long operation emits several `Started`s as it moves between phases. The shell maps `Progress` to a `Serialize`-able `ProgressDto` (a `#[serde(tag = "kind")]` enum in `src-tauri/src/dto.rs`) before it crosses IPC - core stays serde-for-IPC-free (sec 1). Events (`app.emit`) are the alternative when progress isn't tied to one call (global notifications).
- **Cancellation:** use the `CancellationToken` from `<app>-core::service::task`. Hold it in Tauri-managed state, hand a clone to the worker, expose a `cancel` command wired to a Cancel button. Check `is_cancelled()` inside tight loops; the cost is one atomic load.
- **Subprocess shellouts** (ffmpeg, exiftool, dd) follow the same pattern: spawn with stdout/stderr piped, drain stderr on a background thread so the OS pipe doesn't deadlock, read stdout line by line, parse each line into a typed `Progress`, respect the cancellation token. The first app that needs this builds it in `core/service/process.rs`; subsequent apps lift the module. (Hashbrown's regex-parsing of FFmpeg strings ad hoc is what to avoid.)

### 3.6 Security model (capabilities & CSP)

Tauri 2's webview is sandboxed; what it can do is explicit. Treat this as a feature, not friction.

- **Least-privilege capabilities.** `src-tauri/capabilities/default.json` grants the main window a permission set. Add a permission only when a feature needs it. Never grant a plugin's full surface (e.g. unrestricted `fs`) by reflex - for a forensics tool handling evidence, an over-broad `fs` scope is a real risk.
- **Lock the CSP.** `tauri.conf.json`'s `app.security.csp` is set to `'self'` for scripts. Widen deliberately (and narrowly) when a feature needs it; never to `*`.
- **No remote code.** The frontend is bundled and served locally. Don't load scripts, fonts, or styles from the network; everything ships in the binary.
- **Beware `{@html}`.** Rendering untrusted strings as HTML is XSS. Forensic apps display attacker-controlled content (chat messages, filenames) constantly - render as text by default; sanitize explicitly if you must render markup.

### 3.7 Keyboard shortcuts

- **All shortcuts in one place** at the app root via `<svelte:window onkeydown={...} />`, dispatched to typed handlers. Don't sprinkle key bindings through child components. For dynamic-N shortcuts (e.g. "Ctrl+1..9 selects tag N"), one parameterized handler keyed by index, not nine handlers.
- **Standard set every app supports:** `Ctrl+O` open, `Ctrl+S` save, `Ctrl+F` find, `F1` help, `Esc` cancel/close, `Delete` remove selection. (Let the browser keep `Ctrl+C`/`Ctrl+V`/`Ctrl+A` on focused inputs - don't intercept them.)
- **Discoverable.** Every shortcut shows up in (a) the control that invokes it (button `title`, menu item), and (b) a Keyboard Shortcuts help dialog. Message-Maestro's Ctrl+1..9 tag shortcuts were buried in `tag_config.py` and effectively invisible.

### 3.8 Modal dialogs

Dialogs return a typed result to the caller via a callback prop (or a resolved promise) and do not call commands directly. The caller decides what to do with the result. COMRADE's `dialog.result` dict pattern translates to `onConfirm: (value: NewConversation) => void`, not an untyped object. For native OS dialogs (open/save file), use `tauri-plugin-dialog` rather than hand-building a file chooser.

## 4. Backend (Rust core)

The core crate is framework-agnostic and barely changed in the Tauri move - that's the payoff of the split. Everything below is independent of how the UI is rendered.

### 4.1 Error handling

- **`thiserror` for library/core errors. `anyhow` only at a binary boundary.** The shell's `CommandError` (sec 3.4) is the IPC boundary's serializable wrapper.
- **One `Error` enum per crate**, in `error.rs`, with `From` impls for the underlying error types. No `Box<dyn Error>`, no stringly-typed errors.
- **Errors carry context.** `#[error("failed to load conversation {id}: {source}")]`, not `#[error("load failed")]`. FENDER's `Tuple[List, Optional[str]]` is the shape to avoid.

```rust
// <app>-core/src/error.rs
#[derive(Debug, thiserror::Error)]
pub enum Error {
    #[error("io error reading {path}: {source}")]
    Io { path: PathBuf, #[source] source: std::io::Error },

    #[error("parse error in {format} parser: {message}")]
    Parse { format: String, message: String },

    #[error("unsupported format: {0}")]
    UnsupportedFormat(String),
}

pub type Result<T> = std::result::Result<T, Error>;
```

If an existing crate rolled its own `Display` impl, migrate to `thiserror` next time the file changes.

### 4.2 Logging

- **`tracing` from day one.** All four reference projects suffered from `print()`-based or ad-hoc logging.
- **`tracing-subscriber` set up in the shell's `run()`** (`src-tauri/src/lib.rs`) with a sensible default filter (`info` by default, `RUST_LOG` env var overrides). For mirroring logs into the webview devtools console, `tauri-plugin-log` is the option; add it when you want it.
- **Frontend logs land in the same file.** The webview has no log file of its own, so the console bridge (`frontend/src/lib/log.ts`, installed in `main.ts`) mirrors every `console.*` into the `tracing` pipeline via the `log_event` command, under the `frontend` target. One greppable file traces a full chain of actions across the IPC boundary; devtools output is unchanged. The bridge is best-effort - a failed forward is swallowed so logging can never break the UI or recurse.
- **Spans for user-initiated operations:** `#[tracing::instrument(skip(self))]` on service methods. Skip large or sensitive fields; include identifiers and small inputs that help reconstruct what the user did.
- **Log file location:** the app's local data directory. The shell resolves it via Tauri's path API (`app.path().app_log_dir()`); core code that needs a path uses the `directories` crate. On Windows that's `%LOCALAPPDATA%\<app>\logs\`. Rotate daily, keep ~30 days. Defaults, not law.
- **Levels:** `error` = user-visible failure. `warn` = degraded but recoverable. `info` = lifecycle (startup, file opened, export complete). `debug` = developer detail. `trace` = firehose.

### 4.3 Plugin / extension points

When an app has multiple input formats, decoders, or platform-specific code paths (Message-Maestro's parsers, FENDER's decoders), there are two reasonable patterns:

- **For N <= 2:** an `enum` plus `match`. Shorter, monomorphized, easier to refactor than a trait.
- **For N >= 3 (or when new variants come from elsewhere):** a trait plus an explicit registry.

```rust
// <app>-core/src/parser/mod.rs
pub trait Parser: Send + Sync {
    fn name(&self) -> &str;
    fn extensions(&self) -> &[&str];
    fn can_parse(&self, sample: &[u8], path: &Path) -> bool;
    // The template ships `Result<()>`; apps change the return type to their
    // own concrete document model once they have one, updating the trait,
    // the registry's collect type, and existing impls in lockstep.
    fn parse(&self, path: &Path) -> Result<()>;
}
```

- **Registration is explicit, not reflective.** FENDER's filesystem-glob-and-`importlib` approach is a footgun: collisions are silent, ordering is undefined. Construct the registry once at startup and `register()` each parser.
- **Avoid `Box<dyn Trait>` in hot paths.** For the registry, fine. Inside a tight loop, use generics.

### 4.4 Configuration

- **Real config file, not constants-in-code.** FENDER's `sizeingb = 200` and COMRADE's hardcoded `(500, 500)` default position both belonged in config.
- **`toml` for config**, loaded via `serde`. Stored at the app's config directory (`%APPDATA%\<app>\config.toml` on Windows; resolve via Tauri's path API in the shell). Schema versioned (`schema_version = 1`).
- **First-run defaults:** the app ships with a sensible default config; user edits adjust it. Never require the user to create the file.
- **Env vars only for deployment knobs** (`RUST_LOG`). Not for user-facing settings - those live in config and are edited through the UI.

### 4.5 Persistence

- **JSON for human-editable data** (tags, settings, small documents). TOML is for *config*; JSON is for *data*. The split is about audience: TOML for users editing settings by hand, JSON for the app reading and writing structured records.
- **SQLite (via `rusqlite`) for relational or large data.**
- **Sidecar files when data is per-document** (Message-Maestro's `{case}_tags.json` next to the source file). Sidecar beats a central database when the data is tied to a file the user already manages. Use `service::case::Sidecar` from the template; it handles atomic writes and missing-file load semantics.
- **Always include `schema_version`.** Migrations are easier than guessing.
- **Atomic writes for documents.** Write to `foo.json.tmp`, fsync, rename. Optional for config (a corrupt config can be deleted and regenerated; a corrupt document can't).

### 4.6 Exports

When an app writes data to a foreign file format (PDF, KML, Excel, PNG, JSON), the implementation lives in `service/<format>_export.rs` and implements `service::export::Exporter<Document>`. The trait is in the template; each format is one new file. Atomic writes per sec 4.5.

## 5. Project Hygiene

### 5.1 Testing

- **Integration tests in `<app>-core/tests/`** using the real public API. One test file per service or major flow. This is where the bulk of testing value lives - the logic is here and it's headless.
- **Unit tests inline** under `#[cfg(test)] mod tests`.
- **Frontend type safety is the first test.** `npm run check` (svelte-check) runs in CI and must be clean. For non-trivial frontend logic (parsers, formatters, state reducers in `.ts`), add **Vitest** unit tests next to the module.
- **Smoke test that the bundle builds** in CI (`npm run tauri build`). End-to-end webview testing (WebDriver/Playwright against the running app) is still fiddly across platforms; don't pay that tax until a flow is valuable enough to justify it.
- **No coverage target. But:** every bug fix gets a regression test. Every new file format gets a parser test with a real sample in `tests/fixtures/`.
- Reference projects had ~zero tests. FENDER even declared `pytest` in requirements and never used it.

### 5.2 Build & release

- **`npm run tauri build` is the canonical build.** It compiles the release binary and produces the platform bundle. No `build.bat`, no one-liners that drift.
- **Artifacts per platform:** Windows `.msi` + NSIS `.exe`; macOS `.app` + `.dmg`; Linux `.deb` + `.AppImage`. Configured under `bundle` in `tauri.conf.json`.
- **WebView2 on Windows.** The app uses the system WebView2 runtime. Windows 11 ships it; the Tauri installer bundles the Evergreen bootstrapper by default so older machines self-provision. Don't strip that out.
- **The `profile.release` block** (workspace `Cargo.toml`) trades build time for small binaries. Keep it: `opt-level = "z"`, `lto = true`, `codegen-units = 1`, `strip = true`, `panic = "abort"`. Vite minifies the frontend for release automatically.
- **Version lives in three files** - `tauri.conf.json`, the workspace `Cargo.toml`, and `package.json`. Keep them in sync on every release. (A single source-of-truth script is worth writing once the first app cuts a real release.)
- **CI builds on every push to `main` and every PR**, on Windows 11 x64, Linux x86_64, and macOS Apple Silicon (`.github/workflows/ci.yml`). It checks formatting, clippy (deny warnings), `cargo test`, `svelte-check`, and a full bundle build. A green run across all three is the floor.
- **Releases are tagged `v<semver>`.** `0.x.y` until there's a real user; `1.0.0` when the data format is stable.

### 5.3 README discipline

Every app's README has, in order:
1. **One-paragraph what-it-does.** No marketing.
2. **Screenshot** of the current UI (animated GIF for interactive flows is fine).
3. **Install / run** instructions, copy-pasteable.
4. **Supported formats / features** (bullets).
5. **Keyboard shortcuts** table.
6. **Architecture:** one paragraph and a tree of the repo layout.
7. **Build** instructions.
8. **License.**

**Drift rule:** update the README in the same PR as the change it describes when the change touches anything in the list above. Cosmetic-only PRs don't need a new screenshot.

### 5.4 `analysis_todo.md`

Message-Maestro's `analysis_todo.md` is a pattern worth keeping. Every app has one at the repo root, tracked in git. Freeform list of features thought of but not built, known gaps, and things that came up in conversation but aren't worth a full issue. Lower ceremony than GitHub issues; lives with the code; gets rewritten freely. Promote real plans to issues; delete what goes stale.

### 5.5 Telemetry / benchmarking

When an operation's speed matters to users (parsing a large file, exporting a PDF, redacting an hour of video), record it.

- **BenchLog: append-only JSONL, one event per line, written to `<app>/logs/`.** The directory is gitignored. A useful minimum:

  ```json
  {"ts": "2026-05-23T14:02:11Z", "op": "parse_discord_export", "duration_ms": 1843, "input_bytes": 2400000, "ok": true}
  ```

  Add fields as needed (`error`, `record_count`, build metadata). Don't break existing fields; only add.
- **Local-only.** Never ship a remote telemetry uploader. These tools handle sensitive data (forensic evidence, conversation exports). User-readable JSONL on disk only.

### 5.6 Licensing posture (read this before shipping a binary)

The move off Slint **removed a license obligation**: Slint's Royalty-Free terms required a visible "Made with Slint" attribution on every binary. Tauri (MIT/Apache-2.0) and Svelte (MIT) impose **no attribution requirement**, so there is no badge to carry and no commercial-license escape hatch to maintain. What remains:

- **App code: proprietary, all rights reserved** (see `LICENSE.txt`). Copyright held by Steven R. Schiavone. Internal-use grants are extended to Iceberg Forensics LLC and the Westchester County District Attorney's Office High Tech Crime Bureau, each independently, for their own forensic work. The grants do not include redistribution, sublicensing, or inclusion in client-facing deliverables. Update `LICENSE.txt` when the holder or grantee list changes.
- **Inter font: SIL Open Font License 1.1** (see `frontend/src/assets/fonts/Inter-OFL.txt`). The OFL requires the license text to ship with the font; it's bundled into the frontend and surfaced in the About panel.
- **Bootstrap Icons: MIT** (see `frontend/src/assets/licenses/bootstrap-icons-LICENSE.txt`). The MIT terms require the license to ship with copies; the text is mirrored from the npm package and surfaced in the About panel.
- **Tauri / Svelte / Vite: MIT-or-Apache-2.0.** Permissive; no shipped-attribution obligation. No action required beyond not claiming you wrote them.
- **WebView2 (Windows): Microsoft Edge WebView2 Runtime,** redistributable under Microsoft's Distributable Code terms. The Evergreen bootstrapper is the supported distribution path; don't repackage the runtime itself.

The About panel (`frontend/src/lib/components/About.svelte`) imports the license texts at build time via Vite's `?raw` suffix, so they ship inside the webview bundle. If you swap any bundled component (a different font, a different icon set), update both this section and the corresponding license file in the same PR.

### 5.7 Dependencies

- **Add a dependency only when its value is clear.** Each Rust crate and npm package is a future compile-time tax and migration cost.
- **`cargo audit` and `npm audit` run in CI.** No SLA; look at the output when they fail.
- **Update workspace-level `Cargo.toml`** (Rust) and `package.json` (frontend), not ad hoc per-crate edits. Commit both lockfiles (`Cargo.lock`, `package-lock.json`); they are the lockstep guarantee.

## 6. Anti-Patterns

Things to default away from. The framing is "smell," not "forbidden." If you're going against one of these on purpose, leave a comment.

| # | Smell |
|---|-------|
| 1 | Near-duplicate methods for related types (e.g., `delete_person`, `delete_textbox`, `delete_legend`) instead of a generic helper. |
| 2 | Hand-rolling controls the platform or a library already gives you (scrollbars, focus rings, drag-and-edge graphs, date pickers). |
| 3 | No tests, even on the parser layer where they'd be cheap. |
| 4 | Generic error catching plus a top-level alert, with no error type system. |
| 5 | UI state held as a soup of fields with no single owner; or a second source of truth in the webview that drifts from the core. |
| 6 | Hardcoded internal names that mismatch user-facing names (Hashbrown's "Grits"/"Eggs"/"Hashbrown" internals vs "Amplify"/"Trim"/"Redact" UI). |
| 7 | Business logic inside a `#[tauri::command]` instead of a core `service` - fat commands the core can't test headless. |
| 8 | Color/size literals in a component's `<style>` instead of `var(--token)`. |
| 9 | `{@html}` on untrusted content; over-broad capability grants (unrestricted `fs`, `csp: *`). |
